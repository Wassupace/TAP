Implementation plan

TAP v5.8 gap-closure plan

Bring the shipped app in line with PRD v5.8 — the data model is already close to spec, but several modules are wired to mock data, one has a live data-integrity bug, and the whole UI needs a manual theme toggle and exact palette.

  • Status Awaiting review
  • Owner amelliti
  • Repo tap-pwa
  • Rendered 2026-08-22

PRD v5.8 reads like a big jump from what's running today, but the gap is narrower than the document suggests. The Postgres schema (supabase/migrations/001 and 002) already models almost everything v5.8 asks for — planned/active sessions, player shooting targets, per-hand drill data, competitive game results. The real work is in the client: several screens that look finished are wired to hardcoded arrays instead of that schema, three different ad-hoc "add a player" inputs exist where the PRD wants one reusable picker, and the Drills module has been silently saving every heat with an empty player_id since it shipped.

This plan is organized by PRD section so it can be reviewed and executed in parallel by module. Each section states what already works, cites the file that proves it, and scopes the delta.

Fix first, independent of everything else

src/pages/DrillPage.tsx's setup wizard never calls drillStore.setPlayers() — Step 4 is a placeholder ("Player selection coming soon. Solo drill by default."). Every heat_entries row committed by commitHeat() today has player_id: players[currentPlayerIndex]?.id ?? '', which resolves to '' because players is always empty. Every drill logged in production so far is unattributed. This is a one-file fix (wire the Player Picker Modal into that step) and should ship before anything else in this plan, since every day it's unfixed is more unattributable data.

Data model changes

Smaller than expected: one constraint is missing, and one taxonomy extension is TypeScript-only. Nothing else in this plan needs a migration.

DecisionHow do we resolve PRD 1.3's last-write-wins requirement?
No schema change — current behavior already satisfies itChosen

This is a single-scribe, single-device app (PRD 1.2: "single user, single scribe"). There is no concurrent-writer scenario for LWW to arbitrate — dbUpdate's plain .update(...).eq('id', rowId) and syncQueue.ts's retry-on-reconnect already apply writes in the order they reach Postgres, which is last-write-wins for a single writer. Adding an updated_at/version column buys nothing without a second writer to compare against.

Add updated_at + version to every mutable table

Standard LWW plumbing, but it's schema and query overhead in service of a conflict that can't currently occur. Revisit if a second device or a collaborative-scribe feature ever ships.

DecisionWhere does location-history autocomplete's data come from?
Derive from existing sessions.location, no new tableChosen

SELECT DISTINCT location FROM sessions ORDER BY date DESC LIMIT 20 (or the equivalent client-side dedupe over the useSessions cache already loaded for the Calendar) gives the exact "previously used locations surface as tappable suggestions" behavior PRD 3.2 asks for, with zero migration.

New location_history table

Only useful if locations ever need metadata (address, default duration). Nothing in v5.8 asks for that.

DecisionGlobal numpad rule (PRD 1.4): add a shared NumberPad, or leave tap-to-increment as-is?
Add src/components/ui/NumberPad.tsx; keep the existing +/- buttons alongside itChosen

Today MatchActivePage.tsx's score and DrillPage.tsx's makes counter render the number itself with no onClick — only the separate +/- buttons are interactive. The PRD's rule is universal and explicit ("No exceptions"). The fast quick-increment buttons stay for the common case (make, miss); tapping the number itself opens the numpad for correcting a fat-fingered value or entering a value far from zero (e.g. a 47-point margin), which the +/- buttons handle badly today.

Replace +/- entirely with numpad-only entry

Matches PRD's "no exceptions" wording most literally, but a numpad for every single make during a drill is slower than a tap — directly against P4 (speed over completeness). The additive approach gets the same data-correction capability without regressing the common path.

DecisionTheme: adopt the PRD's exact hex palette, or keep the current 'Sport Card' palette and only add the missing manual toggle?
Adopt PRD's exact tokensChosen

The current theme is already centralized as CSS custom properties in src/index.css (--ink, --panel, --chalk, --orange, etc.), flipped by a single @media (prefers-color-scheme: light) block — the right architecture, wrong values. None of the PRD's specified hex codes (#FFFFFF/#0F0F14 background, #E8500A accent, etc.) appear anywhere in the repo today; it's a different palette (#111827/#FF5A1F), not a close miss. Because the values are already centralized in one file, swapping them is low-risk — no component hardcodes a color outside index.css's variables (confirmed: zero dark: Tailwind variants exist, and Button.tsx/Card.tsx/Tag.tsx all reference var(--*) tokens, not literals).

Keep current palette, add toggle only

Less visual churn, but leaves the PRD's Section 1.4 table — which every other part of the document treats as binding spec, not suggestion — permanently unmet, and the "Bug v5.5" callout explicitly frames the missing toggle and palette together as one open issue.

Sheets export (PRD §9)

Credential exposure, not just a spec gap

src/lib/sheetsExport.ts's handleOAuthCallback sends client_secret: CLIENT_SECRET! (from VITE_GOOGLE_CLIENT_SECRET) directly from the browser to Google's token endpoint. Any VITE_* env var ships in the client bundle — this secret is currently readable by anyone who opens dev tools on the deployed app. This needs a server-side hop before anything else in this section, independent of the PRD gap analysis below.

  1. Move the OAuth token exchange server-side

    Reuses: Vercel, already the deploy target — a serverless function needs no new hosting

    Add a Vercel serverless function (e.g. api/google-oauth-callback.ts) that holds GOOGLE_CLIENT_SECRET as a server-only env var and does the token exchange; the client posts the auth code to this endpoint instead of calling Google directly with the secret.

  2. Sheet selection, not just creation

    exportToSheets() always creates a new spreadsheet on first export. Add a picker (Google Picker API or a simple "paste a Sheet URL" fallback) so PRD 9.1's "selects or creates" is both, not just creates.

  3. Fix the 6-vs-7 tab mismatch

    Code writes 7 tabs (Sessions, Matches, Games, Competitive Games, Drills, Players, Career Stats); the PRD and the UI copy both say 6. Recommend folding Games into the Matches tab (each match's rows followed by its game rows) rather than dropping data — see Questions.

  4. True background export + offline queue

    Reuses: the syncWorker.ts polling pattern already built for Supabase sync

    Today doExport() is an awaited promise inside the button handler — leaving the page mid-export aborts it. Move it into a durable queued job (reusing the existing IndexedDB queue infrastructure) so it survives navigation, and so PRD 9.3's "queued while offline, fires automatically on reconnect" is real.

Offline sync consistency (PRD §1.3)

DecisionExtend the IndexedDB-queue pattern to every mutation, or leave it scoped to the three call sites that use it today?
Extend db.ts's dbInsert/dbUpdate/dbDelete to usePlayers.ts and useSessions.tsChosen

Today only three call sites go through the offline queue at all: matchStore.endGame(), drillStore.commitHeat(), and sessionStore.setNotes(). Every player mutation (useAddPlayer, useUpdatePlayer, useDeletePlayer) and every session-lifecycle mutation (useOpenSession, useEndSession, useActivateSession) calls supabase.from(...) directly — if offline, these simply throw with no retry. PRD 1.3 says "all user interactions write to a local queue first," and right now most don't. Routing these through dbInsert/dbUpdate costs a signature change per call site, not new infrastructure — the queue, worker, and StatusDot already exist and already work correctly for the three sites that use them.

Leave as-is; only the three highest-frequency-in-a-gym writes need it

Cheaper, but a scribe adding a walk-in player or ending a session while the gym wifi is down — exactly the scenario PRD 1.3 exists for — currently just fails with no recovery.

  1. Route usePlayers.ts and useSessions.ts mutations through db.ts

    Reuses: dbInsert/dbUpdate/dbDelete, unchanged

    Swap each mutation's direct supabase.from(...) call for the matching dbInsert/dbUpdate/dbDelete, matching the pattern already proven in the three existing call sites.

  2. Offline read path

    Reuses: the idb dependency already in package.json

    None of the useQuery reads (usePlayers, useSessions, etc.) have a local mirror today — offline reads currently just fail/hang. Add a lightweight IndexedDB read cache populated on successful fetch, served when offline, so the UI has something to show (even if stale) per PRD 1.3's "UI always reads from local state."
